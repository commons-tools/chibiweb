# 【表紙・概要】 `README.md`

## chibiweb

**WordPressを入れるほどでもないサイトのために。**

v0.1.0（α版）　｜　デモ：[chibiweb.piemx.net](https://chibiweb.piemx.net/)

chibiweb（ちびウェブ）は、小さなお店や団体のための、小さなウェブ一式です。お知らせだけを更新できる小さなCMSと、静的サイトのひな形、AIと一緒に直すための説明書が入っています。

chibiwebには、2つの約束があります。

1. **小さいままでいる**。サイトは「どんな店か」と「どこにあるか」を伝える場所。毎日の写真や商品はSNSに任せ、通販や予約などの大きな機能は入れない
2. **静的HTMLをAIで更新することを基本に、ブログの構造は最小単位だけ持つ**。ページはただのHTMLで、AIと話しながら直す。日付順・1件ずつ・下書き・予約公開といったブログの構造を持つのは、お知らせだけ

> **はじめに読んでほしいもの**
> - [chibiwebで、小さなお店のサイトを預かる人へ](docs/FOR-MAKERS.md)：ソフトウェアの中には書けない、使い方の考え方
> - [chibiwebで、自分のテーマをつくる人へ](docs/FOR-DESIGNERS.md)：どのファイルのどこを直せば、オリジナルのテーマがつくれるか
> - [chibiwebをフォーク・改造するエンジニアへ](docs/FOR-ENGINEERS.md)：お知らせのしくみの仕様書（データ形式、設定、API、部品）
> - [手順書：お客さんのサイトを作って納品するまで](docs/RUNBOOK.md)：ヒアリングから納品まで、だれでも同じように作れる手順とチェックリスト
> - [chibiwebの安全のしくみ](docs/SECURITY.md)：何を守っていて、何を守っていないか。弱点を見つけたときの連絡先

> これはα版です。仕様は変わります。試して、気づいたことを教えてください。参加のしかたは [CONTRIBUTING.md](CONTRIBUTING.md) へ。

見本の中身は、架空の町のパン屋「こむぎ舎」です。メイン写真は画像生成AIで作ったもので、実在のお店や商品ではありません。営業時間、商品と値段、臨時休業のお知らせ、教室の告知と、小さなお店のサイトに必要なものをひととおり入れています。

### 何が入っているか

```

│   ├─ index.html       トップページの見本

│   ├─ about.html       下層ページの見本（情報リスト・見出し・引用）
│   ├─ news.html        お知らせ一覧ページの見本
│   ├─ site.json        サイト名・ロゴ・メニュー・コピーライト
│   ├─ assets/
│   │   ├─ style.css    見た目（色や文字は先頭の変数で変える）
│   │   ├─ site.js      ヘッダー・フッターの部品
│   │   └─ img/         メイン写真（3サイズ）

│       ├─ admin/       管理画面

│       ├─ lib.php
│       └─ data/        お知らせ本体（1件＝1つの .md ファイル）
├─ docs/                ← 説明（サーバーには上げない）
│   ├─ FOR-MAKERS.md    サイトを預かる人へ（このプロジェクトの考え方）
│   ├─ FOR-DESIGNERS.md 自分のテーマをつくる人へ

│   ├─ RUNBOOK.md       手順書（ヒアリングから納品まで）
│   ├─ SECURITY.md      安全のしくみ

│   ├─ HOW-IT-WORKS.md  しくみの解説（画像つき）
│   ├─ DESIGN.md        デザインのルール

├─ photos/              写真の元データ（サーバーには上げない）
```

- **core**（`public/news/`）：お知らせCMS。これだけ別のサイトに置いても使えます
- **kit**（`public/` のそれ以外）：静的サイトのひな形
- **docs**：人とAIのための説明書。しくみは `docs/HOW-IT-WORKS.md` から

### 動かすのに必要なもの

- PHP 8.1 以上が動くレンタルサーバー（Xサーバー、さくら、ロリポップなど）
- データベースは不要です
- Apache（日本のレンタルサーバーのほとんど）を前提にしています。nginx の場合は、下の「既知の注意点」を見てください

### はじめかた

1. `public/news/config.php` を開き、`'setup_key' => ''` の `''` の中に、自分だけが知っている合言葉を書く
2. `public/` の**中身**をサーバーのサイトのフォルダにアップロードする（`public` フォルダごとではなく中身。`news` フォルダと `news.html` は別物なので両方上がっているか確かめる）
3. `https://あなたのサイト/news/admin/` を開き、1で書いた合言葉と、これから使うパスワード（10文字以上）を入れる
4. 「＋新しく書く」でお知らせを書く
5. `public/site.json` を書き換えて、サイト名とメニューを自分のものにする

#### パスワードについて

- パスワードは `public/news/data/.auth.php` に保存されます。暗号化ではなく、元に戻せない形（ハッシュ。PHP標準の `password_hash`、bcrypt の強さ12）に変換して保存しているので、このファイルを見ても元のパスワードはわかりません。くわしくは [安全のしくみ](docs/SECURITY.md) へ
- 合言葉（setup_key）は、**最初にパスワードを決めるときだけ**使います。合言葉を知らない人は、パスワードを決められません
- パスワードを忘れたら、サーバーの `.auth.php` を削除してください。もう一度、合言葉とパスワードを入れる画面になります
- サイトを別のサーバーやサブドメインに引っ越すとき、`.auth.php` も一緒にコピーすれば、同じパスワードのまま使えます
- お客さんにサイトを渡すときは、`.auth.php` を消して、お客さん自身にパスワードを決めてもらってください
- `.auth.php` はGitHubには入れていません（`.gitignore` で除外）

### お知らせをページに貼る

```html
<div data-news data-channel="info" data-count="3"></div>
<script src="/news/embed.js" defer></script>
```

| 属性 | 意味 | 例 |
|---|---|---|
| `data-channel` | チャンネル（お知らせの種類） | `info` / `urgent` / `event` |
| `data-count` | 件数 | `3` / `all` |
| `data-style` | 見た目 | `compact`（日付＋タイトル）/ `full`（本文も）/ `alert`（緊急用の目立つ箱） |
| `data-link` | タイトルのリンク先。`{id}` が記事IDになる | `/news.html#{id}` |
| `data-more` | 「一覧へ」のリンク先 | `/news.html` |
| `data-empty` | `hide` にすると、0件のとき何も出さない | `hide` |

`data-style="alert"` と `data-empty="hide"` を組み合わせると、臨時休業などの「緊急のお知らせ」を、書いたときだけ目立つ箱で出せます。

同じページに何個でも置けます。チャンネルは `public/news/config.php` で増やせます。

#### 別のサイトから使う

`embed.js` を置いた場所のURLで読み込めば、別ドメインのサイトにも貼れます。
許可するサイトを絞りたいときは `config.php` の `allowed_origins` に書きます。

### ヘッダー・フッター

```html
<site-header><a href="/">サイト名</a></site-header>
<site-footer></site-footer>
<script src="/assets/site.js" defer></script>
```

中身は `site.json` から読みます。メニューを1か所直せば全ページに反映されます。
v0.1 は画面の広さにかかわらずハンバーガーメニューです。

### お知らせのデータ

1件が1つのmdファイルです。管理画面を使わず、直接書いても（AIに書かせても）かまいません。

```markdown
---
date: 2026-11-07
title: サイトを公開しました
link:
status: published
---
本文。空行で段落、**太字**、[リンク](https://example.com)、行頭「- 」で箇条書き。
```

- ファイル名：`日付-英数字6文字.md`（例：`2026-11-07-a1b2c3.md`）
- `status: draft` で下書き、未来の `date` で予約公開
- 削除したものは `public/news/data/_trash/` に移ります

### v0.1 でやらないこと

機能を増やすとWordPressに戻ってしまうので、次のものは今は入れません。

- 画像のアップロード（本文中に画像URLを書くのは将来検討）
- 複数ユーザー・権限
- カテゴリ・タグ（チャンネルで代用）
- 商品の写真や一覧の更新（毎日変わるものは Instagram などのSNSに任せる。サイトは「どんな店か」を伝える場所）
- お知らせのラベル（「重要」などの色つきの札。小さなサイトは情報の種類が少ないので、チャンネル分けで足りる）
- PC用の横並びメニュー（v0.2 の候補）

### 既知の注意点

- お知らせはJavaScriptで差し込むため、検索エンジンへの反映は弱めです
- データフォルダ（`news/data/`）は `.htaccess` で、外から直接読めないようにしています。`.htaccess` が効かない nginx などのサーバーでは、設定に次のような行を足してください

  ```nginx
  location ^~ /news/data/ { deny all; }
  ```
- 総当たり対策は簡易的です。管理画面のURLを推測されにくい名前に変えるのもおすすめです
- 安全のしくみと、弱点を見つけたときの連絡先は [docs/SECURITY.md](docs/SECURITY.md) にあります

# 【考え方（サイトを預かる人へ）】 `docs/FOR-MAKERS.md`

## chibiwebで、小さなお店のサイトを預かる人へ

chibiwebは、小さなお店や団体のウェブサイトを、作る人も、頼む人も、無理なく続けられるようにするための道具です。
このページは、ソフトウェアの中には書けない「使い方の考え方」をまとめたものです。コードより先に読んでください。

ここに書いてあるのは、ひとつのやり方です。正解ではありません。自分のお客さんに合わせて変えてください。

---

### 1. だれのための道具か

- 個人のお店、教室、小さな団体
- サイトの更新は、お知らせが月に数回。ほかのページは年に数回しか変わらない
- 「サブドメイン」と「独自ドメイン」の違いを知らなくても、まったくおかしくない人たち
- 更新に大きなお金はかけられない。でも、ちゃんとしたサイトは欲しい

WordPressは、こうした人たちには大きすぎることがあります。本体とプラグインの更新、管理画面の覚え方、セキュリティの見張り。chibiwebは、そのほとんどを持たないことを選んでいます。

### 2. 小さいままでいる

chibiwebのいちばん大事な約束は、**小さいままでいること**です。

- 毎日変わるもの（お知らせ）だけを、管理画面で書く
- たまにしか変わらないもの（営業時間、メニュー、お店の説明）は、静的HTMLのまま。AIと話しながら直すか、作った人に頼む
- 毎日変わる商品の写真や、日々のできごとは、InstagramなどのSNSに任せる。サイトは「どんな店か」と「どこにあるか」を伝える場所
- 通販、予約、会員機能は入れない。必要になったら、それはもうchibiwebの仕事ではありません

機能を足したくなったら、「それは小さいままか？」と自分に聞いてください。

### 3. 静的HTMLをAIで更新する。ブログの構造は、お知らせだけ

chibiwebのもうひとつの約束は、**静的HTMLをAIで更新することを基本に、ブログの構造は最小単位だけ持つ**、ということです。

- ページは、ただのHTMLファイル。開けばそのまま表示される。データベースも、ページを組み立てるプログラムもない
- ページを直すときは、AIと話しながら直す。「営業時間を変えたい」「地図を入れたい」と頼めば、AIが `AGENTS.md` と `DESIGN.md` のルールを読んで、HTMLを書き換える。管理画面の使い方を覚える必要はない
- 動くのは「お知らせ」だけ。お知らせは、ブログと同じ構造を持っている
  - 1件ずつに日付とタイトルがある
  - 新しい順に並ぶ
  - 一覧と、本文つきの全件表示がある
  - 下書きと、予約公開ができる
- ブログの構造が要るのは、時間とともに増えていくものだけ。お知らせ、イベント、教室の告知。それはチャンネルとして分けられる。それ以外のページに、ブログの構造は要らない

静的HTMLを基本にする理由は、

- **速い**：組み立てる手間がないので、すぐ表示される
- **壊れにくい**：動く部分が少ないほど、壊れる場所も、狙われる場所も少ない
- **長もちする**：HTMLは、10年後のブラウザでも読める
- **持ち運べる**：ファイルをコピーすれば、どのサーバーにも引っ越せる

WordPressは、すべてのページをブログの構造で作り、管理画面から直します。chibiwebは逆に、ほとんどを静的HTMLで作ってAIと話しながら直し、ブログの構造は必要な最小単位にだけ使います。

AIで直せるのは、ページが素のHTMLだからです。決めごとが `DESIGN.md` などのテキストに書いてあるから、どのAIでも同じ調子で直せます。静的HTMLとAIは、この2つでひと組です。

### 4. ホームは「来店までの順番」で組む

小さなお店のサイトに来る人の多くは、こういう道をたどります。

```
Instagramでおいしそうな写真を見る
  ↓
プロフィールのリンクからホームページへ
  ↓
地図と営業時間を見る
  ↓
お店に行ってみる
```

この人は、もう写真を見ています。ホームに来て知りたいのは「どこにあるか」と「行きたい日に開いているか」だけです。だから、ホームはこの順番に並べます。

1. メイン写真（天地は細めに。すぐ情報に入れるように）
2. 緊急のお知らせ（臨時休業など。あるときだけ出る）
3. お店のひとこと
4. 営業時間・定休日
5. アクセス（住所と地図）
6. ふつうのお知らせ
7. イベントや教室
8. ほかのページへの入口

別のページに移るのを、スマホの人は嫌います。ホームが縦に長くなっても、来店に向かう一本の道になっていれば、それは迷わない長さです。

**行ってみたら閉まっていた**。これが、このサイトでいちばん起きてはいけないことです。臨時休業は、ふつうのお知らせと分けて、いちばん上に出してください。

### 5. サブドメインで預かる

ドメインのことがわからないお客さんには、作る人のドメインの下に、サブドメインを切って預かるのがいちばん親切です。

```
https://お店の名前.あなたのドメイン/
```

- お客さんは、ドメインの契約や更新を気にしなくていい
- 作る人は、PHPのバージョンなどをサーバー単位でまとめて管理できる
- chibiwebはプラグインに頼っていないので、PHPのバージョンを上げても壊れにくい。上げる前に、テスト用のサブドメインで一度動かしてから本番に移す

ただし、最初にこれだけは伝えてください。

> このサイトの住所（URL）は、わたしのドメインの中にあります。
> ほかの人に頼みたくなったとき、自分のドメインを持ちたくなったときは、いつでも移せます。そのときは手伝います。

お客さんを、作る人に縛りつけないこと。それが長く信頼される預かり方です。

### 6. 保守ではなく、更新の代行にお金をいただく

WordPressを預かると、見張る仕事（本体やプラグインの更新、壊れたときの対応）が毎月発生します。chibiwebでは、その仕事がほとんどありません。

だから、お金をいただくのは「見張り」ではなく「更新」です。たとえば、

- **月3,000〜5,000円で、お知らせ以外の更新を代行する**（営業時間の変更、メニューの差し替え、写真の入れ替えなど）
- ふだんのお知らせは、お客さんがスマホの管理画面から自分で書く

預かる側がほとんど放っておけるので、預かる件数を増やしても、手間はあまり増えません。

ただ、「ほとんど」であって、ゼロではありません。年に1回くらいは、次のことを確かめてください。

- サーバーのPHPのバージョン
- ドメインとSSLの更新日
- お知らせのデータのバックアップ
- リンク切れや、古くなった情報（値段、営業時間）

### 7. ホームページの寿命は3年と、最初に伝える

ウェブの技術は、3年もすれば大きく変わります。AIも、3年後にどうなっているかは誰にもわかりません。

だから、最初にはっきり伝えてください。

> 3年もつしくみをご用意します。3年たったら、そのときの技術で一緒に作り直しましょう。

「ずっと使えます」と言って5年後に動かなくなるより、ずっと誠実です。

chibiwebは、作り直しに強いしくみです。

- お知らせは、ただのテキストファイル（md）
- ページは、素のHTML
- 決めごとは、`DESIGN.md` と `CONTENT.md` に書いてある

器は3年で替えても、中身はそのまま次へ持っていけます。

### 8. 引き継ぎのメモを渡す

作った人が、ずっとそこにいるとは限りません。お客さんには、次のことを書いた1枚を渡してください。

- サイトのファイルがどこにあるか（サーバー、GitHubなど）
- 管理画面のURL
- ほかの人に頼むときに、渡すもの（`public/` フォルダ一式と、`docs/` の説明書）
- 独自ドメインに移りたいときの連絡先

ドキュメントのいちばんの役目は、作った人がいなくても、次の誰かが続きを引き受けられるようにすることです。

### 9. 更新は、スマホとPCで分ける

- **毎日のこと（お知らせ）**：スマホの管理画面から。むずかしい操作はいらない
- **たまのこと（ページの中身）**：PCで、AIと話しながら。または作った人に頼む

スマホでAIにページを直してもらうのは、まだむずかしいです。だから、毎日のことはスマホで済むようにしてあります。

AIで直すのに、有料のプランは必須ではありません。無料のAIでも、ページのファイルの中身と `AGENTS.md`・`DESIGN.md` を一緒に貼って「ここを直して」と頼めば、ルールどおりに直してくれます。返ってきたものを貼り戻して、アップロードするだけです。

ブロックエディタで自分の手で組むのが好きな人もいます。それもいいやり方です。どちらが合うかは、人によります。

### 10. 見本の文章は、本物を想像して書く

お客さんに渡す前の見本に、「ここに文章が入ります」と書かないでください。デザインは文章を伝えるためにあります。どんな文章が入るかを想像できないまま、形を決めることはできません。

くわしくは `DESIGN.md` の「【重要】見本の文章は、本物を想像して書く」へ。

### 11. 自分仕様にするときの順番

見本の「こむぎ舎」を、自分やお客さんのサイトに作り替えるときの順番です。

1. **`public/` の中身とmd一式を、そのままAIに渡す。** mdだけを渡して「この説明どおりに作って」と頼むと、AIはゼロから作り直すので、似ているけれど別物ができる。お知らせのしくみ（PHP）も作れない
2. **最初に、AIと話しながらmdを書き換える。** お店の名前、ページ一覧、文章のトーンは `CONTENT.md` に、色や文字の決まりは `DESIGN.md` に
3. **書き換えたmdをもとに、HTMLとCSSを直してもらう**
4. **あとは、チャットで少しずつ直す。** 直した中で「これからもこうする」と決めたことだけ、mdに書き戻す

作業の具体的な順番とチェックリストは、[RUNBOOK.md](RUNBOOK.md)（手順書）にまとめています。

それぞれの役目は、こう分かれます。

- **HTML**：いまの形
- **md**：これからも守る決まりごと
- **チャット**：その場の相談

チャットだけで直していくと、決めたことが会話の中に埋もれてしまいます。次の日に別のチャットで続けたり、別のAIに頼んだりしたときに引き継がれません。mdは設計図というより、**引き継ぎのメモ**です。人が替わっても、AIが替わっても、同じ考えで直し続けられるようにするためのものです。

### 12. 直してほしいところに印をつける

mdやHTMLの文章を直してもらうとき、ファイルの中に直接、印を書きこんで渡すこともできます。「どこを、どう」を言葉で説明するより、まちがいが少なくなります。

| 書き方 | 意味 | 例 |
|---|---|---|
| `{前→後}` | 置き換える | `営業時間は{7:00→8:00}から` |
| `{+足す言葉}` | 足す | `食パン{+と焼き菓子}を並べています` |
| `{-消す言葉}` | 消す | `{-とてもとても}おいしいパン` |
| `{?相談}` | 直さずに、相談や質問として答えてほしい | `{?ここは箇条書きのほうが読みやすい？}` |

- かっこは全角 `｛｝` でも半角 `{}` でもかまいません。矢印も `→` でも `->` でもかまいません
- 1つのファイルに、いくつ書いてもかまいません
- 渡すときは「印のところを直して」とひとこと添えます
- AIは印を直したあと、印を消して、直したところを一覧にして返します。`{?…}` は直さずに答えだけ返します

文章を直すときの記号としては、CriticMarkup という決まった書き方もあります。ここでは、スマホでも打ちやすいように、もっと簡単にしています。

この考え方に、足したいこと、ちがうと思うことがあれば、ぜひ聞かせてください。chibiwebは、使う人たちと一緒に育てていくものです。

# 【デザインのルール】 `docs/DESIGN.md`

## DESIGN.md — デザインのルール

人が直しても、AIが直しても、見た目が崩れないための約束です。

### 基本の考え方

- **読むためのサイト**。飾りより、文章が読みやすいことを優先する
- **スマホファースト**。まずスマホで確かめる
- **色は1色**。強調色（アクセント）は1つだけ。増やしたくなったら、文章で強調できないか考える
- **背景は白、文字は黒**。本文やリード文をグレーにしない。グレーは日付・パンくず・注釈だけ
- **書体はゴシック**。見出しも本文も同じ書体で、大きさと太さで差をつける

### 【重要】見本の文章は、本物を想像して書く

デザインは、文章をわかりやすく伝えるためにある。だから、どんな文章が入るのかを想像できないまま形を決めてはいけない。

- **「ここに文章が入ります」「テキストテキスト」は使わない。** 文章が入らないデザインを渡して「あとで文章を入れてください」と言うのは、デザインの仕事を途中で投げることになる
- 見本の文章は、**そのサイトに実際に入る内容を想像して書く**。お店の名前、営業時間、値段、臨時休業の理由まで。行の長さ、見出しが2行になるか、表が何列になるかは、本物らしい文章でないと判断できない
- 長い文章のダミーが必要なときは、**本物の日本語の文章**を使う（著作権の切れた小説の一節など。青空文庫から取ると安心）。句読点の位置、漢字とかなの割合、読む速さまで本物に近づく
- 見本の文章が架空のものであることは、README などにはっきり書いておく（実在のお店や人と取り違えられないように）
- **架空の見本では、事実がわからないところも想像で埋める。** 「こむぎ舎」は架空のお店なので、営業時間・住所・値段・お知らせの中身まで、本物らしく書いてよい。**「要確認」「（見本）」「○○を入れてください」も使わない**（「ここに文章が入ります」と同じこと）。住所だけは実在の場所と取り違えないよう「○○市○○町1-2-3」のように伏せる

AIがページを作るときも、人がテンプレートを作るときも、このルールを守ること。

### 変えてよい変数（`public/assets/style.css` の `:root`）

| 変数 | 役割 | 初期値 |
|---|---|---|
| `--color-text` | 文字の色（黒） | `#000000` |
| `--color-text-sub` | 補足の文字（日付・パンくず・注釈だけ） | `#5f5f5f` |
| `--color-bg` | 背景（白で固定） | `#ffffff` |
| `--color-surface` | カード・表の背景（白の上で区別できる薄いグレー） | `#f7f6f3` |
| `--color-line` | 罫線 | `#e3ded5` |
| `--color-accent` | リンク・ボタン・強調 | `#8a3f2c` |
| `--color-accent-soft` | 注意書きの箱の背景 | `#f4e9e3` |
| `--font-body` | 本文の書体 | システムのゴシック |
| `--font-head` | 見出しの書体 | 本文と同じゴシック |
| `--content-width` | 本文の最大幅 | `42rem`（全角約40字） |

#### 文字の大きさ（仮。ジャンプ率はあとで調整する）

| 変数 | 使うところ | 大きさ |
|---|---|---|
| `--font-size-h1` | ページの見出し、トップの大見出し | 36px |
| `--font-size-h2` | 大見出し、トップのセクション名 | 28px |
| `--font-size-h3` | 小見出し、お知らせ一覧のタイトル | 22px |
| `--font-size-h4` | さらに小さい見出し、ロゴ | 18px |
| `--font-size-body` | 本文 | 16px |
| `--font-size-small` | 日付・パンくず・注釈 | 14px |

大きさを変えるときは、この表と `:root` の変数を一緒に直す。

#### 字間
- 見出し：`--letter-spacing-head`（0.08em）。太いゴシックでも重く見えないよう、少しあける
- 本文：`--letter-spacing-body`（0.04em）。行間は1.9

- 文字と背景の色の差は、WCAG AA（4.5:1以上）を守る
- 書体を変えるときは、日本語が表示できるか確かめる

### ページの型

#### トップページ（小さなお店の型）
インスタなどで写真を見て、プロフィールのリンクから来た人が「来店」までたどる順番に並べる。
別ページに移らずに、ホームだけで来店に必要なことがわかるようにする（縦に長くなってよい）。

1. メイン写真（天地は細め。写真はもうSNSで見ているので、すぐ情報に入れるように）
2. 緊急のお知らせ（臨時休業など。書いたときだけ出る）
3. お店のひとこと（`.hero`：大見出し＋説明）
4. 営業時間・定休日
5. アクセス（住所の情報リスト＋地図。メニューの「アクセス」から `/#access` で飛べる）
6. お知らせ（ふつうのお知らせは、あえて下に）
7. イベント・教室
8. 下層ページへの入口（`.child-pages`）

お知らせは「緊急」と「ふつう」で置き場所を分ける。行ってみたら閉まっていた、をなくすのが緊急のお知らせの役目。

#### メイン写真（トップのヒーロー画像）
- 1サイトに1枚。お店や団体の「顔」になる写真（パン屋なら、パンの集合写真）
- 元の比率は **3:2**。表示はスマホで **2:1**、広い画面で **3:1** に上下を切り抜く
- 横幅 **800・1600・2400px** の3枚を WebP で用意し、`public/assets/img/hero-800.webp` などの名前で置く
- **大事なものは写真の中央の帯に入れる**（上下が切れるため）
- 重さの目安：800pxで150KB、2400pxで400KB以下
- 写真の上に文字を重ねない（読みにくくなるため）。キャッチは写真の下に置く

#### 下層ページ
1. ページ見出し（`.page-head`：h1＋リード文。必要なら2段見出し）
2. 本文（`<article class="prose">`）
3. ページ末ナビ（`.page-nav`：ホーム・関連ページへ）

**どの下層ページもこの順番を守る。** 迷子にならないことが一番大事。

#### パンくずは使わない（1段のサイトでは）
ページがすべてホームの1段下にあるあいだは、パンくずを置かない。メニューとページ末ナビで足りる。
親ページ→子ページ、と階層が2段以上になったら、子ページにだけパンくず（`.breadcrumb`）を置き、
親ページの本文の最後に子ページへの入口（`.child-pages`）を置く。

#### ヘッダー
ロゴ（サイト名）と、三本線のアイコン＋「メニュー」の文字のボタンだけ。v0.1 は画面の広さにかかわらずハンバーガーメニュー。

#### フッター
コピーライトだけ。`Copyright © 年 名前` の形で、**英語で書く**（例：`Copyright © 2026 Komugisha`。年は自動で入る）。大きなサイトのような、リンクを並べたフッター（メガフッター）は作らない。

### 使える部品（`.prose` の中）

| 部品 | 書き方 | 使いどころ |
|---|---|---|
| 2段見出し | `<h1><span class="kicker">小さい1行目</span>本題</h1>` | ページ見出しで、名前や本題に添え書きをつけたいとき |
| 大見出し | `<h2>` | 話題の区切り |
| 小見出し | `<h3>` | h2の中の区切り。h2なしでh3だけ使わない |
| さらに小さい見出し | `<h4>` | h3の中の区切り。めったに使わない |
| 段落・箇条書き | `<p>` `<ul>` `<ol>` | — |
| 引用 | `<blockquote>` | 他の人の言葉 |
| 表 | `<div class="table-wrap"><table>…` | 必ず `table-wrap` で包む（スマホで横スクロール） |
| 情報リスト | `<dl class="info-list"><div><dt>…<dd>…` | 営業時間・所在地・連絡先 |
| 注意書きの箱 | `<div class="note">` | 1ページに1つまで |
| ボタン | `<a class="button">` / `class="button ghost"` | 1画面に主ボタン1つまで |
| 子ページの入口 | `<ul class="child-pages"><li><a><strong>ページ名</strong><span>ひとこと説明</span></a>` | 親ページの最後、ホームの「パンとお店のこと」。枠のついたカードになる。ページ名だけでなく、何が書いてあるかを1行添える |
| 画像 | `<figure><img alt="…"><figcaption>` | `alt` は必ず書く |
| 地図 | `<div class="map"><iframe …></div>` | ホームの「アクセス」に1か所だけ置く（下層ページには置かない。直し忘れを防ぐため）。本文のカラム幅いっぱい、4:3。画面の端から端まで広げたいときは `class="map map--wide"`。道案内は地図の中の「拡大地図を表示」から開ける。iframe の `width` `height` `style` は消して、`title` と `loading="lazy"` をつける。場所は `https://www.google.com/maps?q=住所や施設名&output=embed` の形で書ける |
| 縦書き | `class="tate"` | キャッチコピーなど短い言葉だけ。本文には使わない |

この一覧にない部品が必要になったら、作る前に相談する（Issueに書く）。

### してはいけないこと

- `style="…"` でその場だけ見た目を変える
- 見出しを、文字を大きくするために使う（見出しは文章の構造）
- 「こちら」だけのリンク文字（リンク先が何かわかる言葉にする）
- 色だけで意味を伝える

# 【ページ一覧と文章のルール】 `docs/CONTENT.md`

## CONTENT.md — ページ一覧と文章のルール

サイトの「中身」の約束です。サイトを使い始めたら、自分のサイトに合わせて書き換えてください。

### ページ一覧

| ファイル | ページ名 | 親ページ | 内容 |

| `news.html` | お知らせ | ホーム | お知らせ全件 |

ページを足したら、ここに1行足す。

### お知らせのチャンネル

| チャンネル | 名前 | 何を書くか |
|---|---|---|
| `info` | お知らせ | 季節のパン、年末年始の営業 |
| `urgent` | 緊急のお知らせ | 臨時休業、急な営業時間の変更。**終わったら下書きに戻すか削除する**（残っているとホームの上に出続けるため） |
| `event` | パン教室 | 教室の告知（日時・定員・参加費・申込方法） |

### 文章のルール

- です・ます調
- 1文は短く。60字をこえたら分けられないか考える
- 漢字とかなのバランス：「出来る→できる」「事→こと」「下さい→ください」
- 数字は半角（2026年11月7日、14時）
- 日付は「11月7日（土）」の形
- 専門用語を使うときは、はじめて出てくる場所で短く説明する
- 「お気軽に」「ぜひ」は1ページに1回まで

### 用語の統一

| 使う | 使わない |
|---|---|
| お問い合わせ | お問合せ、問い合わせ |
| お取り置き | 取り置き、おとりおき |
| 税込 | 税込み、内税 |
| メール | E-mail、Eメール |
| （サイトに合わせて足す） | |

- 個人の名前・連絡先を載せてよいか、本人に確認したか
- 日付と曜日が合っているか
- リンクが切れていないか

# 【しくみの解説】 `docs/HOW-IT-WORKS.md`

## しくみの解説

chibiweb v0.1 が、どう動いているかの説明です。
はじめて触る人と、未来の自分のために。

### 全体の考え方

このサイトは、2種類のページでできています。

- **ふだんは変わらないページ**：HTMLのまま置いてある（ホーム、パンのご案内、お店について）。直すときはAIと話しながら直す
- **よく変わる部分**：お知らせだけ。管理画面から書くと、ページの決まった場所に差し込まれる

WordPressは「全部のページを毎回組み立てる」しくみですが、chibiwebは「変わるところだけ動かす」しくみです。そのぶん軽く、壊れにくく、保守がほとんどいりません。
なぜこう作ったのかは、`FOR-MAKERS.md` に書いてあります。

### 見た目の部品

ホームは、SNSで写真を見てやってきた人が「お店に行く」までたどる順番に並んでいます。

1. メイン写真（天地は細め）
2. 緊急のお知らせ（臨時休業など。書いたときだけ出る）
3. お店のひとこと
4. 営業時間・定休日
5. アクセス（住所と地図）
6. お知らせ
7. パン教室
8. パンとお店のこと（ほかのページへの入口）

このうち「緊急のお知らせ」「お知らせ」「パン教室」の中身だけが、管理画面から書いたものです。ほかは静的HTMLです。
地図は、ホームの「アクセス」1か所だけに置いています（メニューの「アクセス」から飛べます）。

#### ヘッダーとフッター

ヘッダー（ロゴとメニュー）とフッター（コピーライト）は、全ページ共通の「部品」です。
各ページのHTMLには、次の2行が書いてあるだけです。

```html
<site-header>…</site-header>
<site-footer></site-footer>
```

中身は `public/site.json` 1か所に書いてあり、そこを直すと全ページのメニューが変わります。
いま開いているページには、メニューに印（●）がつきます。

#### 下層ページ

下層ページは、どれも同じ順番でできています。

1. ページの見出し（小さい1行目＋大きい本題）
2. 本文
3. ページ末の移動リンク

見出し・表・情報リスト・注意書きなどの部品の使い方は、`DESIGN.md` に書いてあります。

### お知らせが表示されるまで

```
管理画面で書く
   ↓
public/news/data/info/2026-11-07-a1b2c3.md として保存される（1件＝1ファイル）
   ↓
ページを開くと、embed.js が api.php に「最新3件ちょうだい」と頼む
   ↓
api.php が mdファイルを読んで、新しい順に返す
   ↓
embed.js が、ページの <div data-news> の場所に並べる
```

お知らせ1件はただのテキストファイルなので、管理画面を使わずに、AIやエディタで直接書いてもかまいません。

#### 管理画面

`/news/admin/` を開くとログイン画面になります。上のタブで「お知らせ」「緊急のお知らせ」「パン教室」を切り替えます。タブ（チャンネル）は `news/config.php` で増やせます。

はじめて開いたときは、`config.php` に書いた合言葉（setup_key）と、これから使うパスワードを入れる画面になります。

- **日付を未来にすると**：その日になるまで公開されない（予約公開）
- **状態を「下書き」にすると**：公開側には出ない
- **削除すると**：完全には消えず、`data/_trash/` に移る（あとで取り戻せる）
- **緊急のお知らせは**：臨時休業の日が過ぎたら、下書きに戻すか削除する。残っているとホームの上に出続ける

管理画面の背景がクリーム色なのは、公開ページと見分けるためです。

### フォルダの分け方

```
chibiweb/
├─ public/      ← サーバーに上げるもの（この中身を、サイトのフォルダにそのまま入れる）
├─ docs/        ← 説明のmd（サーバーには上げない）
│   └─ img/     ← 説明用の画像
├─ photos/      ← 写真の元データ（サーバーには上げない）
├─ README.md          ← 最初に読む説明
├─ AGENTS.md          ← AIへの作業ルール
├─ CLAUDE.md          ← Claude用の入口（中身は AGENTS.md を読むだけ）
├─ CONTRIBUTING.md    ← 参加のしかた
├─ CODE_OF_CONDUCT.md ← 行動規範
├─ CHANGELOG.md       ← 変更の記録
└─ LICENSE
```

`README.md` や `AGENTS.md` などは一番上に置いています。GitHubは一番上の `README.md` を表紙として表示し、AIの道具の多くは一番上の `AGENTS.md` を探しに行くためです。

### 写真

- メイン写真は1枚。横幅 800・1600・2400px の3サイズを用意して、ブラウザが画面に合うものを選ぶ
- 元の写真は `photos/` に置き、AIが3サイズに変換して `public/assets/img/` に入れる
- 毎日変わる商品の写真はサイトでは扱わず、InstagramなどのSNSに任せる

### 安全のためにしていること

- 管理画面はパスワードつき。パスワードは元に戻せない形（ハッシュ）で `news/data/.auth.php` に保存
- 最初のパスワードは、`config.php` に書いた合言葉（setup_key）を知っている人しか決められない
- お知らせのデータフォルダは、外から直接は読めない（`.htaccess`）
- 本文に危ないリンク（`javascript:` など）を書いても、リンクにならない
- フォームには「なりすまし送信」を防ぐ確認がついている

くわしくは `SECURITY.md` へ。パスワードの強さの目安や、使う人ができることも書いてあります。

### まだできないこと（v0.1）

- 画像のアップロード
- 複数の人での管理
- PCで横並びのメニュー
- お知らせのラベル（「重要」など）

詳しくは `README.md` の「v0.1 でやらないこと」へ。決めていない先のことは `CHANGELOG.md` の「これから」にまとめています。

# 【テーマをつくる人へ】 `docs/FOR-DESIGNERS.md`

## chibiwebで、自分のテーマをつくる人へ

chibiwebの見た目は、CSSファイル1枚で決まっています。
いま入っているテーマは、最初につくった人の好み（背景は白、文字は黒、見出しもゴシック、色は1色）が反映されたものです。ひとつの例にすぎません。
このページを読んで、自分のテーマをつくってください。

---

### 1. まず知っておくファイル

| ファイル | 場所 | 役割 |
|---|---|---|
| `DESIGN.md` | `docs/DESIGN.md` | デザインのルール。ページの型、使える部品、してはいけないこと。**テーマをつくる前に、必ず読む** |
| `style.css` | `public/assets/style.css` | 見た目のすべて。テーマをつくるときに直すのは、基本的にこのファイルだけ |
| 各ページのHTML | `public/*.html` | 中身と構造。テーマをつくるときは**直さない** |
| `site.json` | `public/site.json` | サイト名、ロゴ、メニュー、コピーライト。見た目ではなく中身 |

HTMLは、どのページも同じクラス名（`.page`、`.section`、`.prose`、`.info-list` など）で組んであります。
この名前を変えなければ、`style.css` を差し替えるだけで、すべてのページが新しいテーマに切り替わります。**クラス名は、HTMLとCSSのあいだの約束**です。

### 2. はじめる前に

`docs/DESIGN.md` の中でも、特にこの2つを読んでください。

- **【重要】見本の文章は、本物を想像して書く**：テーマを確かめるときも、「テキストテキスト」ではなく、本物らしい文章で見る
- **ページの型**：ホームと下層ページの並び順。テーマで見た目は変えても、この順番は変えない

### 3. 手で書かなくていい。AIと話しながらつくる

テーマは、CSSを手で書いてつくらなくてかまいません。chibiwebは、ページの更新と同じように、テーマもAIと話しながらつくることを基本にしています。

#### 数字ではなく、言葉で伝える

AIに頼むとき、色コードやピクセルの数字を用意する必要はありません。

> クリーム色で、草原の香りがするような色にしたい

こんなふうに、言葉で伝えてください。`#f4efe1` という数字を探すのは、AIの仕事です。

人の仕事は、そのお店がどんな空気をまとっているかを感じとって、言葉にすることです。朝の焼きたてのパンの湯気、木の棚のあたたかさ、窓から入る光。それを色や文字や余白にどう置きかえるか、その感性こそがデザインです。

道具が手作業からAIに変わっても、デザインの原点は変わりません。むしろ、数字の調整から解放されたぶん、「どう感じてほしいか」を考えることに時間を使えるようになりました。

#### 頼み方の例

AIに、`docs/DESIGN.md` とこのファイル、`public/assets/style.css` を読ませてから、こんなふうに頼んでください。

- 「クリーム色で、草原の香りがするような背景にしたい」
- 「古い喫茶店のマッチ箱みたいな、少しくすんだ赤をアクセントに」
- 「背景をクリーム色、文字をこげ茶にして、やわらかい雰囲気にしたい」
- 「見出しだけ明朝にしたい」
- 「全体の余白を少し広くしたい」
- 「この写真（またはこのサイト）の色の雰囲気に近づけたい」
- 「いま何を変えたのか、どの変数を直したのか教えて」

AIは、`DESIGN.md` のルールを守りながら、`style.css` の変数を書き換えます。

#### 決めるのは人

AIが出す色は、「クリーム色」「草原」「香り」という言葉が、たくさんの人の書いてきた文章の中でどう結びついてきたかから選ばれます。いわば、人の知恵の平均値として浮かび上がる色です。

平均値は、だれにでも通じる安心感があります。でも、そのお店だけの色にはなりにくい。それをそのまま採るのか、少しずらすのか。ずらすなら、どちらへ、どのくらいか。

**言葉で伝えるのが、ひとつめの感性。出てきたものを見て、採るか、ずらすかを決めるのが、ふたつめの感性です。** デザイナーの個性は、このふたつめに出ます。

平均から離れたいときは、こんな頼み方もできます。

- 「3案出して」：平均のまわりに、いくつか候補を並べてもらう
- 「もう少し、ありきたりでない方向に」：平均から離れる方向を、言葉で伝える
- 「その色にした理由を教えて」：AIが言葉をどう受け取ったかを聞いて、自分の感じ方とのずれを確かめる

そのうえで、

- 直してもらったら、**必ずスマホで見て確かめる**
- 気に入らなければ、「元に戻して」「もう少し弱く」と言えばいい
- 何を変えたのかを、AIに説明させる。自分でもわかるようにしておくと、次に直すときに迷わない
- 下の「`style.css` のどこを直せばいいか」は、AIに頼むときの言葉の手がかりにもなる。「変数の章の `--color-accent` を変えて」のように、場所を指して頼むと、思いどおりになりやすい

### 4. `style.css` のどこを直せばいいか

`style.css` は、9つの章に分かれています。テーマをつくるときに直す場所は、上から順に、こうなります。

#### ① まずは「1. デザインの変数」だけで（ファイルの先頭）

ここを変えるだけで、テーマの印象の大部分が決まります。**最初は、ここ以外をさわらずにつくってみてください。**

| 変数 | 決めるもの |
|---|---|
| `--color-text` | 文字の色 |
| `--color-text-sub` | 補足の文字（日付・注釈）の色 |
| `--color-bg` | 背景の色 |
| `--color-surface` | カード・表・地図の背景 |
| `--color-line` | 罫線の色 |
| `--color-accent` | リンク・ボタン・強調の色（1色） |
| `--color-accent-soft` | 緊急のお知らせ・注意書きの箱の背景 |
| `--font-body` | 本文の書体 |
| `--font-head` | 見出しの書体（いまは本文と同じゴシック。明朝にしたいならここ） |
| `--font-size-h1` 〜 `--font-size-small` | 文字の大きさ（見出し4段階＋本文＋小さい文字） |
| `--letter-spacing-head` / `--letter-spacing-body` | 字間（見出し・本文） |
| `--space` | 余白の単位。すべての余白はこの倍数 |
| `--content-width` | 本文の最大幅（いまは全角約40字） |
| `--radius` | 角丸の大きさ（カード、地図など） |
| `--header-height` | ヘッダーの高さ |

色を変えたら、文字と背景の色の差が十分あるか（WCAG AA、4.5:1以上）を確かめてください。

#### ② レイアウトを変えたいときは「5. ページの骨組み」

- `.page`：本文の幅と、画面の左右の余白
- `.page-wide`：本文より広く使いたいところの幅
- `.page-head`：下層ページの見出し部分

ページの外枠を決めているのは、ここだけです。

#### ③ ホームの見せ方を変えたいときは「7. トップページ」

- `.hero-image`：メイン写真の比率（いまはスマホで2:1、広い画面で3:1）
- `.hero`：お店のひとこと
- `.section` / `.section-title`：ホームの各ブロックの間隔と見出し

#### ④ 部品の見た目を変えたいときは「6. 本文」と「8. お知らせ部品」

- 「6. 本文」：見出し、表、情報リスト、注意書きの箱、ボタン、地図など、`.prose` の中の部品
- 「8. お知らせ部品」：お知らせの一覧、緊急のお知らせの箱

#### さわらなくていいところ

- 「2. 土台」「9. 補助」：どのテーマでも共通の基本。変えるときは理由があるときだけ
- 「3. ヘッダー」「4. フッター」：メニューの開け閉めの動きと関係しているので、色や余白以外を変えるときは、スマホでメニューが開けるかを必ず確かめる

### 5. 多段カラムについて

chibiwebは、最初から1段で組んでいます。スマホでは結局1段に積むしかなく、小さなお店のサイトでは、読む順番が1本に決まっているほうが迷わないからです。

サイドバーのような2段組みは、おすすめしません。広い画面で横に並べたいときは、ホームの「下層ページへの入口」のカードのように、部分的に並べるくらいがちょうどいいと思います。

### 6. してはいけないこと

- HTMLのクラス名を変える（テーマを入れ替えられなくなる）
- `style="…"` で、その場だけ見た目を変える
- 色を増やしすぎる（強調の色は1色から始める）
- スマホで確かめずに、PCの画面だけで決める

### 7. できたテーマを持ち寄る

- `style.css` を1枚のファイルとして、テーマの名前をつけて共有する（例：`theme-kinari.css`）
- ファイルの先頭のコメントに、テーマの名前、つくった人、どんなお店や団体に向いているかを書く
- 見本のパン屋さんのページで、スマホとPCのスクリーンショットを添える

テーマが2つ以上集まったら、`site.json` に1行書くだけで切り替えられるしくみをつくる予定です。

---

テーマづくりは、コードを書かない人でも参加できる、chibiwebのいちばん開かれた入口です。

# 【仕様書（エンジニアへ）】 `docs/FOR-ENGINEERS.md`

## chibiwebをフォーク・改造するエンジニアへ

お知らせのしくみ（core）と、ヘッダー・フッターの部品（kit）の仕様書です。
直す前に、[FOR-MAKERS.md](FOR-MAKERS.md) の「2つの約束」を読んでください。機能を足すときの判断の物差しは「小さいままでいられるか」です。

対象のバージョン：v0.1.0

---

### 1. 全体の構成

```
public/
├─ news/                ← core（お知らせ）。これだけ別のサイトに置いても動く
│   ├─ config.php       設定（この章の「3. 設定ファイル」）
│   ├─ lib.php          共通の関数
│   ├─ api.php          公開用API（JSONを返す）
│   ├─ embed.js         ページに差し込む部品
│   ├─ admin/index.php  管理画面（1ファイル）
│   └─ data/            お知らせ本体と認証情報
│       ├─ .htaccess    外からの直接アクセスを拒否
│       ├─ .auth.php    パスワードのハッシュ（自動で作られる。Gitには入れない）
│       ├─ <チャンネル>/<ID>.md
│       └─ _trash/      削除したお知らせ
├─ assets/site.js       ← kit。ヘッダー・フッターの部品
└─ site.json            ← kit の設定
```

- 動かすのに必要なもの：PHP 8.1 以上。データベース、Composer、ビルド作業は不要
- 外部ライブラリ：使っていない（PHPもJavaScriptも標準機能だけ）
- 文字コード：UTF-8

### 2. データの形式（お知らせ1件＝1ファイル）

#### 置き場所とファイル名

```
public/news/data/<チャンネル>/<ID>.md
```

- **ID**：`YYYY-MM-DD-xxxxxx`（正規表現 `^\d{4}-\d{2}-\d{2}-[a-z0-9]{6}$`）。この形でないファイルは無視される
- 管理画面で作ると、`xxxxxx` には16進数6文字が入る。手で作る場合は英小文字と数字6文字なら何でもよい
- まちがえやすい例：`2026-11-09-urgent01`（8文字）、`2026-11-01-info001`（7文字）、`2026-11-01-A1B2C3`（大文字）は、どれも無視される
- チャンネルのフォルダは、管理画面にログインしたときに自動で作られる（手で作ってもよい）

#### 中身

```markdown
---
date: 2026-11-07
title: 季節のパンが入れかわりました
link: /menu.html
status: published
---
本文（Markdownの一部が使える）
```

| 項目 | 必須 | 意味 | 省略したとき |
|---|---|---|---|
| `date` | — | 表示する日付。`YYYY-MM-DD` | IDの先頭10文字 |
| `title` | — | タイトル | `(無題)` |
| `link` | — | タイトルからのリンク先。外部URLやPDFでもよい。`http://` `https://` `/` `./` `../` `#` `mailto:` で始まるものだけ使える（それ以外は空として扱う） | リンクなし |
| `status` | — | `published`（公開）／`draft`（下書き） | `published` |

- 先頭の `---` で囲んだ部分は、`キー: 値` の1行ずつ。キーは英小文字と `_` だけ。値の前後の空白は取り除かれる。引用符は、値の全体が同じ引用符の組（`"…"` か `'…'`）で囲まれているときだけ外す。片方だけ、または途中にあるものは残る（`"春のパン"まつり` はそのまま）
- **公開の条件**：`status` が `published`、かつ `date` が今日以前（未来の日付は予約公開として隠れる）。「今日」は `config.php` の `timezone` で決まる
- **並び順**：`date` ＋ ID の降順（新しい順）

#### 本文で使えるMarkdown（ごく一部）

| 書き方 | 結果 |
|---|---|
| 空行 | 段落の区切り |
| 段落内の改行 | `<br>` |
| `**太字**` | `<strong>` |
| `[文字](URL)` | リンク。URLは `http://` `https://` `/` `./` `../` `#` `mailto:` で始まるものだけ。それ以外（`javascript:` など）はリンクにせず文字だけ残す |
| 行頭の `- ` または `* ` | 箇条書き（ブロックの全行がそうなっているとき） |

本文はすべてHTMLエスケープしてから変換している。HTMLをそのまま書いても、タグとしては出ない。
ほかの書き方（見出し、画像、表など）は対応していない。足すなら、[1章の約束](FOR-MAKERS.md)と相談してから。

### 3. 設定ファイル（`public/news/config.php`）

PHPの配列を返すだけのファイル。

| キー | 型 | 意味 |
|---|---|---|
| `site_name` | 文字列 | 管理画面に出すサイト名 |
| `setup_key` | 文字列 | **最初のパスワードを決めるときの合言葉**。空のままだと、管理画面でパスワードを決められない。決めたあとは使わない |
| `site_url` | 文字列 | 管理画面の「サイトを見る」のリンク先 |
| `timezone` | 文字列 | 予約公開の判定に使うタイムゾーン（例：`Asia/Tokyo`） |
| `channels` | 配列 | `キー => 表示名`。キーは英小文字。最初のものが既定のチャンネルになる |
| `allowed_origins` | 配列 | APIを読んでよい別ドメイン（例：`['https://example.com']`）。空なら、どこからでも読める |
| `max_items` | 整数 | APIが一度に返す最大件数 |

### 4. 公開API（`public/news/api.php`）

読み取り専用。認証なし。

#### リクエスト

```
GET api.php?channel=info&count=3
GET api.php?channel=info&count=all
GET api.php?channel=info&id=2026-11-07-a1b2c3
```

| パラメータ | 意味 | 既定 |
|---|---|---|
| `channel` | チャンネルのキー。`config.php` にないものは、最初のチャンネルとして扱う | 最初のチャンネル |
| `count` | 件数。`all` なら `max_items` まで。1〜`max_items` に丸める | `5` |
| `id` | 1件だけ返す（公開中のものだけ） | — |

#### レスポンス

```json
{
  "channel": "info",
  "label": "お知らせ",
  "items": [
    {
      "id": "2026-11-07-a1b2c3",
      "date": "2026-11-07",
      "title": "季節のパンが入れかわりました",
      "link": "/menu.html",
      "html": "<p>本文をHTMLに変換したもの</p>"
    }
  ]
}
```

- 下書きと予約公開中のものは含まれない
- ヘッダー：`Content-Type: application/json; charset=utf-8`、`Cache-Control: public, max-age=60`
- CORS：`allowed_origins` が空なら `Access-Control-Allow-Origin: *`。指定があれば、一致したOriginだけを返す

**この形（データ形式とAPIのレスポンス）が、chibiwebの約束です。** PHP以外で作り直すときも、ここを守れば `embed.js` とページはそのまま使えます。

### 5. 埋め込み部品（`public/news/embed.js`）

```html
<div data-news data-channel="info" data-count="3"></div>
<script src="/news/embed.js" defer></script>
```

- `data-news` のついた要素を、ページ読み込み時にすべて探して、それぞれAPIを呼ぶ
- APIのURLは、`embed.js` 自身のURLから決める（同じフォルダの `api.php`）。別ドメインからでも使える

| 属性 | 値 | 既定 |
|---|---|---|
| `data-channel` | チャンネルのキー | 最初のチャンネル |
| `data-count` | 件数／`all` | `5` |
| `data-style` | `compact`（日付＋タイトル）／`full`（本文も）／`alert`（緊急用。本文つきの箱） | `compact` |
| `data-link` | タイトルのリンク先。`{id}` がIDに置き換わる。お知らせ側に `link` があればそちらが優先 | なし |
| `data-more` | 「〜の一覧へ」のリンク先（`compact` のときだけ） | なし |
| `data-empty` | `hide` なら、0件や読み込み失敗のとき要素ごと隠す | 「まだありません」と表示 |

#### 出力するHTMLとクラス名

```html
<div class="mini-news mini-news--compact">
  <ul class="mini-news__list">
    <li class="mini-news__item" id="2026-11-07-a1b2c3">
      <time class="mini-news__date" datetime="2026-11-07">2026.11.07</time>
      <span class="mini-news__title"><a href="…">タイトル</a></span>
      <!-- full / alert のときだけ -->
      <div class="mini-news__body">…</div>
      <a class="mini-news__link">詳しく見る</a>
    </li>
  </ul>
  <a class="mini-news__more">お知らせの一覧へ</a>
</div>
```

- 見た目は `style.css` の「8. お知らせ部品」で決める。クラス名は変えないこと（テーマとの約束）
- 各項目の `id` がお知らせのIDなので、`/news.html#ID` でページ内の位置に飛べる
- 本文のHTMLはサーバー側でエスケープ済みのものを、そのまま差し込んでいる

### 6. 管理画面（`public/news/admin/index.php`）

1ファイルで、ログイン、一覧、作成・編集、削除をすべて扱う。

#### 認証

- ユーザーは1人だけ。パスワードのハッシュ（`password_hash` / `PASSWORD_DEFAULT`、`cost` 12）を `data/.auth.php` に保存。PHPのバージョンにかかわらず強さ12（PHP 8.4 からの標準と同じ）
- ログイン成功時に `password_needs_rehash` で確かめ、前の強さで保存されたハッシュは今の強さで作り直す
- `.auth.php` がないときは「はじめに」の画面になる。`config.php` の `setup_key` と一致する合言葉を入れた人だけがパスワードを決められる。`setup_key` が空なら、決められない
- パスワードは10文字以上
- ログインに失敗したとき、合言葉をまちがえたときは、2秒待たせる（簡易的な総当たり対策）
- セッション名は `chibiweb`。ログイン成功時にセッションIDを作り直す。Cookieは `HttpOnly`、`SameSite=Strict`、HTTPSなら `Secure`
- ログインの印は、`true` ではなく `login_mark()`（`.auth.php` のパスと中身から作ったSHA-256）をセッションに入れ、毎回照らし合わせる。同じサーバーの別のchibiwebとセッションの保管場所を共有していても、そちらのログインでは入れない。パスワードを決め直すと、古いログインは自動で切れる
- パスワード管理アプリが保存しやすいように、画面には出さないユーザー名欄（値は `admin`）を送っている

#### 操作

| 操作 | 方法 | 内容 |
|---|---|---|
| 一覧 | GET `?channel=` | 下書き・予約中も含めて新しい順 |
| 新規 | GET `?action=new` | 空のフォーム |
| 編集 | GET `?action=edit&id=` | |
| 保存 | POST `action=save` | IDがなければ `日付-16進6文字` で新しく作る。ファイルは排他ロックで書く |
| 削除 | POST `action=delete` | `data/_trash/<チャンネル>--<ID>.md` に移す（消さない） |
| ログアウト | POST `action=logout` | |

- POSTはすべて、セッションに持たせたCSRFトークンを確かめる
- 画面の出力は `htmlspecialchars` でエスケープしている

### 7. ヘッダー・フッター（kit：`public/assets/site.js`）

```html
<site-header><a href="/">サイト名</a></site-header>
<site-footer></site-footer>
<script src="/assets/site.js" defer></script>
```

- カスタム要素 `site-header` と `site-footer` を定義している
- 設定は `site.json`。場所は `site.js` から見て `../site.json`。`<script data-config="…">` で変えられる
- `site.json` が読めないときは、HTMLに直接書いた中身（ロゴのリンクなど）がそのまま残る

```json
{
  "name": "こむぎ舎",
  "logo": "",
  "home": "/",
  "menu": [ { "label": "ホーム", "href": "/" } ],
  "copyright": "Komugisha"
}
```

- `logo` が空ならサイト名を文字で出す
- メニューは、いま開いているページに `aria-current="page"` をつける（`#` つきのリンクは対象外）
- フッターは `Copyright © 年 copyright` を出す。年は自動

### 8. セキュリティについて知っておくこと

使う人向けの説明は [SECURITY.md](SECURITY.md) にあります。弱点の報告先もそこに書いてあります。

- `data/` は `.htaccess` で外から読めないようにしている。nginxなどでは、同じことを設定で行うこと（README参照）
- `.auth.php` は `.php` なので、万一アクセスされても中身は表示されない
- 総当たり対策は簡易的。本格的にするなら、ログイン試行の回数を記録する、管理画面のフォルダ名を変える、サーバー側でIP制限をかける、など
- APIは公開情報しか返さないので、認証をつけていない

### 9. フォーク・移植するときに

- **守ってほしいもの**：2章のデータ形式と、4章のAPIの形。ここが同じなら、既存のサイトのお知らせとページがそのまま使える
- **自由に替えてよいもの**：管理画面の作り、保存の方法、動かす言語
- 例：GitHubのファイルをそのまま `data/` として使い、ビルドでJSONを書き出す「サーバーなし版」も、この形を守れば `embed.js` と組み合わせられる
- 変えたら、`CHANGELOG.md` に書き残してください。説明書（`docs/`）も一緒に直すと、次の人が助かります

# 【安全のしくみ】 `docs/SECURITY.md`

## chibiwebの安全のしくみ

「自分でサーバーに置くのは、こわい」。そう感じるのは自然なことです。
このページでは、chibiwebが何を守っていて、何を守っていないのかを、正直に書きます。こわさの正体がわかれば、何に気をつければいいかもわかります。

対象のバージョン：v0.1 以降

---

### 1. chibiwebが狙われにくい理由

ウェブサイトへの攻撃の多くは、人ではなくプログラムが自動で行っています。よく使われているソフト（WordPressとそのプラグインなど）の、知られた弱点を探して回るものです。

chibiwebには、その的になるものがほとんどありません。

- **データベースがない**：データベースを狙う攻撃（SQLインジェクション）が、そもそも成り立たない
- **プラグインがない**：外から足した部品の弱点を突かれることがない
- **動く部分が少ない**：ページはただのHTML。動くのは、お知らせの小さなしくみ（PHPのファイル4つ）だけ

動く部分が少ないほど、壊れる場所も、狙われる場所も少なくなります。小さいままでいることは、安全のための設計でもあります。

### 2. 守っているもの

| 何を | どうやって |
|---|---|
| 管理画面 | パスワードがないと入れない |
| パスワード | 元に戻せない形（ハッシュ）で保存。方式は bcrypt、強さは12 |
| 最初のパスワード決め | `config.php` に書いた合言葉（setup_key）を知っている人しか決められない |
| お知らせのデータ | `news/data/` は、外から直接は読めない（`.htaccess`） |
| パスワードのファイル | `.auth.php` は `.php` なので、万一開かれても中身は表示されない |
| なりすまし送信 | 管理画面のフォームには、本人が送ったかを確かめるしるし（CSRFトークン）がついている |
| お知らせの本文 | HTMLやスクリプトを書いても、文字として表示されるだけで動かない。`javascript:` で始まる危ないリンクも、リンクにならない。「リンク先」の欄も、本文と同じ決まりで確かめている |
| ログインの状態 | ログインのたびに新しい合い札（セッションID）を作る。Cookieは、スクリプトから読めず（HttpOnly）、ほかのサイトから送られず（SameSite=Strict）、HTTPSなら暗号化した通信でだけ送られる（Secure） |
| ほかのchibiwebとの境目 | 同じサーバーに別のchibiwebがあっても、そちらのログインでは入れない。ログインの印は「このサイトの、このパスワード」に結びついている |
| 総当たり | パスワードや合言葉をまちがえると、2秒待たされる |

### 3. パスワードの強さの目安

パスワードは、ハッシュという「元に戻せない形」にして保存しています。ハッシュは、パスワードから計算で作れますが、ハッシュからパスワードを逆に計算することはできません。

ハッシュが盗まれたとき、攻撃者にできるのは「パスワードを1つずつ試して、同じハッシュになるか確かめる」ことだけです。chibiwebが使っている bcrypt は、この1回の計算に、わざと時間がかかるように作られています。

万一ハッシュが盗まれて、高性能なGPUで総当たりされた場合の目安です。

| パスワード | 破られるまでの目安 |
|---|---|
| 英小文字と数字のでたらめ10文字 | 数万年以上 |
| 英大小文字・数字・記号のでたらめ12文字 | 実質、破れない |
| 単語を4つ以上つなげた長い文 | 実質、破れない |
| `komugi2026` のような、単語＋数字 | 数分〜数時間（よくある言葉から順に試されるため） |

**方式が強くても、推測しやすいパスワードは守れません。** いちばん効く対策は、長くて推測されにくいパスワードにすることです。

#### 強さ12について

bcrypt の「強さ」は、数字が1つ上がるごとに計算が2倍遅くなります。強さ12は、強さ10の4倍、破るのに時間がかかります。ログインは0.2秒ほど遅くなりますが、人が気づくほどではありません。

PHP 8.4 から、PHPの標準の強さが10から12に上がりました。chibiwebは、PHPのバージョンにかかわらず、いつも強さ12で保存します。前の版（強さ10）で決めたパスワードは、次にログインしたときに、自動で強さ12に作り直されます。パスワードを決め直す必要はありません。

### 4. 守っていないもの・弱いところ

正直に書きます。

- **総当たりの対策は簡易的**：まちがえると2秒待たせるだけです。何台ものパソコンから同時に試されると、防ぎきれません。だから、パスワードの長さが大事になります
- **2段階認証はない**：パスワードだけで入れます
- **管理する人は1人だけ**：誰がいつ書いたかの記録はありません
- **HTTPSはサーバーまかせ**：chibiwebは、通信の暗号化（HTTPS）を自分では用意しません。レンタルサーバーの無料SSLを、必ず有効にしてください
- **nginx では設定が要る**：データの保護は `.htaccess`（Apache）が前提です。nginx などでは、README の「既知の注意点」にある設定を足してください
- **サーバーそのものの安全**：サーバーのOSやPHPの更新は、レンタルサーバーの会社の仕事です

### 5. 使う人ができること

上から順に、効き目が大きいものです。

1. **パスワードを長くする**：パスワード管理アプリが作るでたらめな文字列か、単語を4つ以上つなげた長い文に
2. **HTTPSを有効にする**：レンタルサーバーの管理画面で、無料SSLをオンに。アドレスが `https://` で始まっているか確かめる
3. **合言葉（setup_key）も、推測されにくいものにする**：パスワードを決めるまでのあいだ、これが管理画面の鍵になります
4. **PHPを新しく保つ**：レンタルサーバーの管理画面で、サポートが続いているバージョン（8.1以上）を選ぶ
5. **管理画面のフォルダ名を変える**（任意）：`news/admin/` を、推測されにくい名前に変えると、自動の攻撃に見つかりにくくなる
6. **バックアップを取る**：`news/data/` のフォルダを、ときどき手元にコピーしておく
7. **`.auth.php` を人に渡さない**：お客さんにサイトを渡すときは、このファイルを消して、お客さん自身にパスワードを決めてもらう

### 6. 弱点を見つけたら

chibiwebの安全にかかわる弱点を見つけたら、**GitHubのIssuesには書かずに**、次のアドレスに知らせてください。Issuesはだれでも読めるので、直す前に弱点が広まってしまうからです。

**commons@piemx.net**

- 何をしたら、どうなったか
- 使っているバージョン（`CHANGELOG.md` の版の番号）

を書いてもらえると助かります。ボランティアで運営しているので、返事に時間がかかることがあります。直したら、`CHANGELOG.md` に記録します。

使い方の質問や、安全とは関係のないまちがいは、ふつうに Issues に書いてください。

# 【AIへの作業ルール】 `AGENTS.md`

## AGENTS.md — AIへの作業ルール

このサイトをAI（Claudeなど）に直してもらうときのルールです。
AIは作業の前にこのファイルと `docs/DESIGN.md`、`docs/CONTENT.md` を読んでください。
しくみの全体は `docs/HOW-IT-WORKS.md`、このプロジェクトの考え方（なぜ小さいままでいるのか）は `docs/FOR-MAKERS.md`、お知らせのしくみの仕様は `docs/FOR-ENGINEERS.md`、安全のしくみは `docs/SECURITY.md`、お客さんのサイトを作って納品するまでの手順は `docs/RUNBOOK.md` にあります。

説明書を1枚にまとめた `docs/chibiweb-all.md` もあります（各mdをつなげたもの）。**`docs/` のmdを直したら、`chibiweb-all.md` も作り直すこと。**

### フォルダ

- `public/`：サーバーに上げるもの。サイトの本体はすべてここ
- `docs/`：説明のmd。サーバーには上げない
- `photos/`：写真の元データ。サーバーには上げない

### このサイトのしくみ

- ページは静的HTML。ビルド（変換作業）はありません。ファイルを直せばそのまま反映されます
- ヘッダー・フッターは `public/site.json` と `public/assets/site.js` が作ります。**各ページのHTMLにメニューを直接書かない**
- お知らせは `public/news/data/<チャンネル>/*.md`。ページには `<div data-news>` で差し込まれます

### 触ってよいところ

| やりたいこと | 直すファイル |
|---|---|
| ページの文章を直す | `public/` の各 `.html` の `<main>` の中 |
| 新しいページを作る | `public/about.html` をコピーして作る（下記の手順） |
| メニューを変える | `public/site.json` の `menu` |
| 色・文字を変える | `public/assets/style.css` の `:root` の変数だけ |
| お知らせを書く | `public/news/data/<チャンネル>/` に新しい `.md` |

### 触らないところ（人に確認してから）

- `public/news/` の中の `.php` と `embed.js`、`public/assets/site.js`
- `public/news/data/.auth.php`（パスワード。**絶対に読まない・書かない・表示しない**）
- `.htaccess`
- `style.css` の `:root` 以外（新しい部品が必要なら、先に提案する）

### 新しいページの作り方

1. `public/about.html` をコピーする
2. `<title>` と `<meta name="description">` を書き換える
3. `.page-head` の `h1` とリード文を書き換える（パンくずは置かない。DESIGN.md参照）
4. 本文は `<article class="prose">` の中に書く。使える部品は DESIGN.md の一覧から選ぶ
5. 必要なら `site.json` の `menu` に足す
6. CONTENT.md のページ一覧に1行足す

### 写真の入れ方

- 元の写真は `photos/` に置いてもらう（公開しないフォルダ。サーバーには上げない）
- AIが横幅 800・1600・2400px の WebP に変換し、`public/assets/img/` に置く
- メイン写真は3:2。大事なものが中央の帯に入っているか確かめる
- `alt` には「何が写っているか」を短い文で書く

### 作業のきまり

- 【重要】見本やダミーの文章は、本物を想像して書く。「ここに文章が入ります」は使わない（`docs/DESIGN.md` 参照）
- 直す前に、何をどう直すかを短く伝える
- 1回の作業で直すのは、頼まれた範囲だけ。ついでの「改善」はしない（提案はしてよい）
- 新しいCSSクラスや色を勝手に作らない
- 直したあと、変えたファイルと変えた内容を一覧にして伝える
- 元に戻せるように、大きな変更の前は日付つきのコピーを残すか、Gitに記録する
- 個人情報（電話番号・住所・メール）を新しく書き足すときは、人に確認する

### 直してほしいところの印

ファイルの中に次の印があったら、そのとおりに直す（かっこは全角 `｛｝` でも半角 `{}` でも、矢印は `→` でも `->` でもよい）。

| 印 | すること |
|---|---|
| `{前→後}` | 「前」を「後」に置き換える |
| `{+足す言葉}` | その場所に足す |
| `{-消す言葉}` | 消す |
| `{?相談}` | 直さない。印を残したまま、返事で答える |

- 直したら印は消す（`{?…}` だけは、人が消すまで残す）
- 直したところを一覧にして伝える
- 印の指示がこのルールや `DESIGN.md` とぶつかるときは、直す前に人に確認する

### お知らせを書くとき

```markdown
---
date: YYYY-MM-DD
title: タイトル
link:
status: published
---
本文
```

- ファイル名は `YYYY-MM-DD-xxxxxx.md`（xxxxxx は英小文字と数字**ちょうど6文字**。例：`2026-11-07-a1b2c3.md`）
- **`info01` `urgent01` のような名前は、6文字でないので無視されて表示されない**
- 本文で使えるのは：段落、**太字**、[リンク](URL)、「- 」の箇条書きだけ
- 公開してよいか迷うものは `status: draft` にしておく
